# School Lab Word Report Builder

## Purpose

Use this skill to turn experiment materials into a polished Word `.docx` lab report while preserving the user's template. This skill is for final Word reports. For `实验过程及内容`, do not generate short content directly inside DOCX code; first use `school-lab-md-expander` to expand the preliminary Markdown into a detailed Word-ready Markdown source, then insert that expanded Markdown into the Word template.

The main job is not to redesign the document. The main job is to fill the template's existing report regions with high-quality content, code, figures, formulas, tables, and analysis while keeping the original template structure intact.

If the user provides a completed or partially completed report as a style example, such as `Lab1.docx`, treat that file as the formatting authority for the same section. For `实验过程及内容`, clone the actual local pattern from the reference document: the same table cell/region, paragraph rhythm, line spacing, heading weight, body text treatment, numbering appearance, equation placement, and code/table/caption treatment. Do not replace the reference style with generic Markdown heading styles or a newly invented document design.

## Required Inputs

Expect some or all of these inputs:

- A target `.docx` report, such as a partially completed report.
- A reference/template `.docx` that defines layout and style.
- Markdown experiment notes generated by `school-lab-report`.
- Expanded Markdown generated by `school-lab-md-expander`, especially for `实验过程及内容`.
- Source code files.
- Result images, CSV files, printed metrics, logs, or tables.
- The original lab assignment PDF/DOCX.

If the user provides both a current report and a reference template, use the current report as the document to complete and the reference template as the formatting/layout authority.

## Non-Negotiable Template Rules

- Do not modify the cover unless the user explicitly asks.
- Do not remove, replace, or restyle existing template headings, teacher review areas, score areas, signatures, notes, or footer instructions.
- Do not redesign frames, text boxes, borders, page geometry, or template regions.
- Fill content only inside the original regions/boxes/placeholders intended for report content.
- Preserve original titles such as `实验目的`, `方法、步骤`, `实验过程及内容`, `数据处理分析`, `实验结论`, `指导教师批阅意见`, `备注`, and similar template text.
- Treat the report as additive: add content to the required sections, do not rewrite fixed template text.
- Preserve all original assignment/template assets, including embedded pictures, drawings, charts, equation objects, text boxes, and images inside problem statements. A problem diagram such as a programming-question figure is part of the original question, not optional result material.
- Do not use APIs such as `paragraph.text = ...` or `cell.text = ...` on existing template paragraphs/cells when they may contain runs, drawings, formulas, or field codes; those assignments delete the embedded objects. Append new paragraphs/runs after anchors instead, or explicitly clone the original runs and drawing relationships before rewriting.
- When a reference report is supplied, inspect the target section in that reference before insertion. Use it as a style sample, not only as a content sample.
- Do not clear and rebuild a section with a different paragraph style system unless the rebuilt content visually matches the reference section after rendering.

## Sections To Complete

Usually complete only:

1. `方法、步骤`
2. `实验过程及内容`
3. `数据处理分析`
4. `实验结论` or `实验总结`

Usually do not complete or alter:

- Cover page.
- Fixed template labels.
- Teacher review/comments.
- Signature/date/grade sections.
- Template notes and instructions.

## Content Requirements

Write from the student's first-person perspective where personal completion is discussed. Avoid second-person wording such as `你做了...`.

Use these content roles:

- `方法、步骤`: concise design summary of each experiment item. Write compact numbered points. Do not include long principle derivations here.
- `实验过程及内容`: the most important section. Expand from Markdown notes and include detailed knowledge points, algorithm/theory explanations, formula derivations, code for programming tasks, and code design explanation.
- `数据处理分析`: the second most important section. Extract and discuss actual results from images, CSV files, tables, logs, or printed metrics. Include result figures and corresponding tables.
- `实验结论` / `实验总结`: use first-person completed tense, such as `我完成了...`, `我实现了...`, `我分析了...`, and summarize the whole experiment.

For concept questions:

- Do not include code.
- Preserve the original problem statement and number, then answer directly under it.
- Do not add module labels such as `题目分析`, `实验原理`, `实验设计`, `核心代码`, `代码说明`, or `本题小结`.
- Provide detailed analysis, definitions, formula derivations, comparisons, and conclusions as direct answer paragraphs.

For programming questions:

- Preserve the original problem statement and number, then append content under it.
- Under each problem, use the bold labels `题目分析`, `实验原理`, `实验设计`, `核心代码`, and `代码说明` without separate numbering.
- Include code in `实验过程及内容`, not as screenshots.
- Explain code design and how each part corresponds to the algorithm.
- Put result images/tables and result interpretation in `数据处理分析`.

Strict section boundary:

- `实验过程及内容` is for requirements, knowledge points, theory, derivations, algorithm flow, code design, and code text.
- `实验过程及内容` must not import result-display material from expanded Markdown, including sections titled `实验结果`, `结果展示`, `结果分析`, `数据处理分析`, `实验结果分析`, `结果文件`, `输出结果`, or similar.
- Result images, result tables, CSV summaries, metric tables, figure captions, and interpretation of observed output belong in `数据处理分析`.
- If an expanded Markdown file contains result material, split it before DOCX insertion: keep process/theory/code content for `实验过程及内容`, and route result material to `school-lab-data-analysis`.

## Expansion-First Rule For `实验过程及内容`

Before filling `实验过程及内容`, always follow this process:

1. Locate the original preliminary Markdown files for concept and programming tasks.
2. Use `school-lab-md-expander` to produce expanded Markdown files. The expansion must be materially richer than the draft and must include detailed knowledge points, formulas, derivations, code design, and code text.
3. Save the expanded Markdown as a standalone artifact, for example under `expanded/`.
4. Insert the expanded Markdown content into the `实验过程及内容` region of the DOCX.
5. Do not replace the expanded Markdown with a short DOCX-generated summary.

The DOCX insertion code should be a renderer/converter from expanded Markdown to Word content, not the primary content author. If the inserted DOCX content is much shorter than the expanded Markdown, the workflow has failed and must be corrected.

When inserting expanded Markdown:

- Preserve every original problem statement already present in the target report/template, including numbers such as `1.1`, `2.2`, and `3.3`. Do not delete, rewrite, renumber, or replace these paragraphs.
- If an original problem statement contains an embedded picture/diagram, preserve the picture with the problem anchor and insert generated content after it. Do not move such problem images to `数据处理分析`, and do not drop them during Markdown-to-DOCX conversion.
- Before and after DOCX editing, make an inventory of media/drawing/equation relationships in the edited sections. The count and identity of original template assets must not decrease unless the user explicitly asked to remove them.
- Treat original problem statements as anchors. Insert generated content after the matching problem paragraph.
- For concept-question anchors, insert only direct answer paragraphs and formulas.
- For programming-question anchors, insert exactly the bold labels `题目分析`, `实验原理`, `实验设计`, `核心代码`, and `代码说明`, followed by their content.
- Markdown headings become Word paragraphs styled consistently with the template and user numbering rules.
- Normal Markdown paragraphs become 宋体 五号 Word paragraphs.
- Code fences become syntax-highlighted Word code tables with a left line-number gutter; read `references/code-blocks.md` before implementing code insertion.
- LaTeX display equations become visible Word equations or verified equation renderings.
- Markdown tables become centered three-line Word tables only when they describe methods, parameters, or code design. Result tables are routed to `数据处理分析`.
- Markdown image references are not inserted into `实验过程及内容` unless the image is a method diagram required to explain the algorithm. Result images remain in `数据处理分析`.
- Before insertion, run a content-boundary pass that removes or moves result sections, image-only result blocks, metric summaries, and result captions from the process-section Markdown.

## Formatting Requirements

Apply these styles to newly inserted content unless the template requires a stricter local style:

- Normal added Chinese text: 宋体, 五号.
- Code blocks: native Word text, Consolas 8.5-9pt, syntax-highlighted by language, with a left line-number gutter. Use `references/code-blocks.md`.
- Figure captions: 宋体, 六号, bold, centered. Do not inherit Calibri/等线 or left alignment.
- Tables: centered three-line table style matching the user's designed table style.
- Figures and tables must use adaptive sizing, not blanket maximum width. Start from the asset's natural size, cap it to the available page/cell width, and choose a visually balanced width for the content. Never upscale a small raster image beyond its natural dimensions just to fill the line.
- For result figures, prefer a readable width that normally falls around 50%-85% of the text area unless the image truly needs more detail. Method diagrams may use a larger cap, but still must not stretch or distort.
- Tables should be centered and sized to content when compact. Use full available width only for genuinely wide comparison tables; otherwise set table width/column widths so the table looks intentional and text wraps cleanly.
- Equations: visible Word equation format, not raw unrendered LaTeX text in the final DOCX.
- Preserve all fixed template content styles.

Do not convert existing fixed template labels to new fonts unless they are part of newly added content.

## Equation Rendering Rule

Final DOCX formulas must be rendered formulas, not plain LaTeX or symbol strings. Prefer native Word OMML equations (`m:oMath` / `m:oMathPara`) so the formula remains editable in Word.

Required equation workflow:

1. Keep equations in expanded Markdown as LaTeX source.
2. During DOCX insertion, convert each equation to a visible Word equation.
3. Prefer `MathML -> OMML` conversion using Microsoft Office `MML2OMML.XSL` and `lxml`.
4. If a LaTeX-to-MathML converter is available, use it before `MML2OMML.XSL`.
5. If no converter is available, convert common formulas through controlled templates or manually authored MathML/OMML.
6. Only use rendered equation images as a fallback when native OMML cannot be produced, and verify the image is sharp and aligned.
7. Never leave raw `$$...$$`, `\frac{...}`, `\sqrt{...}`, or similar formula source in the final DOCX.

Inline and variable equation workflow:

- Convert inline formulas from `$...$` or `\(...\)` into inline OMML inserted inside the same Word paragraph, between surrounding text runs.
- Convert short mathematical variables with subscripts/superscripts into inline OMML when they are mathematical symbols, for example `x_i`, `Q_{11}`, `H^{-1}`, `I(x,y)`, `p_k`, or `\mu_1`. Do not leave them as plain text merely because they are short.
- Do not convert code identifiers, file names, paths, Markdown links, or fenced code content as formulas.
- Do not fake formulas by placing simplified text inside `<m:oMath><m:r><m:t>...</m:t></m:r></m:oMath>`. That produces a math container, not a properly rendered equation. Use real OMML structures produced from MathML/OMML templates.
- Respect Word's two equation modes: inline equations remain inside the surrounding paragraph, while display equations occupy their own centered equation paragraph. Do not convert all formulas to display mode.
- Plain-looking mathematical tokens from prose must be upgraded to inline OMML when they are formulas, especially tokens like `G_x`, `G_y`, `R_{ci}`, `\mu_{R_i}`, `F(p)`, `D(F(p), \mu_{R_i})`, `I(x,y)`, and `Q_{11}`. A token receiving Word spell-check underlines because it was inserted as ordinary text is a formatting failure.
- The Markdown source should prefer `$G_x$`, `$G_y$`, `$R_{ci}$`, and `$\mu_{R_i}$` for inline variables; however, the DOCX insertion pass must also detect common unmarked subscript/superscript variables in mathematical prose.

Before delivery, structurally check the generated DOCX for `m:oMath` when native equations are expected, and visually render/inspect pages.

## Numbering Rules

Use this hierarchy from high to low:

1. Chinese section level: `一、`, `二、`, `三、`
2. Decimal level: `1.`, `2.`, `3.`
3. Parenthesized level: `(1)`, `(2)`, `(3)`
4. Parenthesized-as-text level: `1)`, `2)`, `3)`
5. Letter level: `a.`, `b.`, `c.`

When a lab problem is named `3.1`, `3.2`, etc., convert the report-internal task numbering to the report sequence style required by the user, for example `1.`, `2.`, `3.` or the local template's intended numbering. Keep numbering consistent within the section.

## DOCX Workflow

1. Execute or verify the experiment and use `school-lab-report` to produce preliminary per-task Markdown.
2. For each task, use `school-lab-md-expander` to create expanded Markdown for `实验过程及内容`.
3. For each task or the whole lab, use `school-lab-data-analysis` to create the `数据处理分析` Markdown from result images, tables, CSV files, logs, and metrics.
4. Use `school-lab-method-conclusion` to create the final `方法、步骤` and `实验结论` Markdown.
5. Read the lab assignment, generated Markdown artifacts, code, and results.
6. Inspect the current DOCX and reference template before editing. Identify the paragraphs, tables, text boxes, or regions that correspond to required sections. If a completed reference such as `Lab1.docx` is available, sample the actual `实验过程及内容` paragraphs and clone that local style.
7. Preserve the original document structure and all original problem statements. Make a working copy before edits.
   - Before changing a populated section, snapshot the original section's media/drawing/formula relationship ids so assignment images and existing equations can be verified after insertion.
   - Preserve embedded problem images such as a `2.5` prompt figure exactly where the template placed them.
8. Insert generated Markdown section by section:
   - `方法、步骤` from `school-lab-method-conclusion`.
   - `实验过程及内容` from `school-lab-md-expander` expanded Markdown after stripping/moving result material, inserted under the original problem anchors.
   - `数据处理分析` from `school-lab-data-analysis`.
   - `实验结论` from `school-lab-method-conclusion`.
9. Convert formulas to visible Word equations using the equation rendering rule. Do not leave raw LaTeX in the final DOCX.
10. Insert code as native Word text using syntax-highlighted two-column code tables with accurate line numbers; do not insert code screenshots or plain unhighlighted paragraphs.
11. Insert figures into `数据处理分析` with adaptive, non-stretched sizing and centered 宋体 六号 bold captions.
12. Insert tables as centered three-line tables with adaptive content-based width. Keep table captions and tables visually paired.
13. Render the DOCX to PNG pages using the documents skill renderer.
14. Inspect every rendered page. Fix overflow, missing glyphs, broken equations, clipped/highlightless code, incorrect code line numbers, bad page breaks, stretched images, and table formatting drift.
15. Scan the final DOCX XML/text for raw math tokens outside code blocks, including `$$`, `\(`, `\)`, `\frac`, `\sqrt`, `\sum`, `_{`, and `^{`. Any hit in report prose is a failure unless it is intentionally inside code.
16. Re-render after every meaningful layout fix. Deliver only after the latest render is clean, or disclose if render QA cannot be completed because LibreOffice is unavailable.
17. Prepare the final teacher-facing hand-in package when this is the final delivery step. The clean package contains only the final report DOCX, `result/`, and `code/`.

## Final Hand-In Package

When this skill is the final delivery step, prepare a clean teacher-facing package in addition to the working artifacts.

Default final package path:

```text
output/<lab>_提交材料/
├── <lab>_实验报告.docx
├── result/
└── code/
```

Package rules:

- Include exactly the final report DOCX, a singular `result/` folder, and a `code/` folder unless the assignment explicitly requires another file.
- `result/` contains only curated final outputs referenced by the report, such as final images, compact CSV/XLSX tables, or metric files. Do not include render-QA PNGs/PDFs, temporary XML, scratch notebooks, cache files, or obsolete intermediate outputs.
- `code/` contains the source needed to reproduce the submitted results: scripts, notebooks, helper modules, config files, and small required input examples when appropriate. Do not include virtual environments, `__pycache__`, large raw datasets unless required, generated outputs, or hidden tool caches.
- Preserve the working folders such as `expanded/`, `analysis/`, `summary/`, and raw `results/` for development, but do not copy them into the teacher-facing package.
- If the report references files by relative path, make those paths valid inside the final package or keep references descriptive rather than broken.
- Before delivery, list the package tree and check that the teacher-facing package has no unrelated files.
