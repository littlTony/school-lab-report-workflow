# Word 版课程实验报告规则

## 总体定位

本 skill 负责完成最终 Word 版课程实验报告。它不是 Markdown 初稿生成器，而是把已有实验内容、代码、结果图、表格和分析填入 `.docx` 模板。

重要流程变更：`实验过程及内容` 不能由 DOCX 写入脚本临时生成短内容。必须先用 `school-lab-md-expander` 把已有 Markdown 初稿扩写成详细版本，再把扩写后的 Markdown 内容插入 Word。`数据处理分析` 同样不能在 DOCX 阶段被压缩成短摘要，必须把 `school-lab-data-analysis` 或现有分析 Markdown 中的结果文件、结果展示、结果数据表和结果分析完整迁入。

核心原则：

1. 模板优先：模板已有内容、框、标题、教师批阅区、备注区不能动。
2. 内容补充：只在报告要求的区域中增加内容。
3. 格式统一：新增正文、代码、图注、表格、公式必须按用户指定格式处理。
4. 视觉验证：最终 DOCX 必须渲染检查，不能只靠 XML 或文本抽取判断。
5. 资产保留：模板/题目中已有的图片、绘图对象、公式对象、文本框、图表和题干配图都属于原始内容，报告只能在其后添加内容，不能因为重建段落或单元格而删除它们。

## 内容来源优先级

优先从以下材料提取内容：

1. 当前实验 Markdown 文件，例如概念题详细解答、编程题说明、结果分析。
2. 使用 `school-lab-md-expander` 生成的扩写版 Markdown。
3. 已运行代码产生的图片、CSV、日志、指标。
4. 原始实验题目 PDF/DOCX。
5. 当前 Word 报告中用户已经写好的内容。
6. 参考模板 DOCX 中的版式与固定结构。

不要凭空编造不存在的实验结果。若没有运行结果，应先运行代码或说明缺失。

## 推荐执行流水线

每次完整实验报告建议按以下顺序执行：

1. 执行实验代码，生成图片、CSV、日志和指标。
2. 使用 `school-lab-report` 为每道题生成基础 Markdown。
3. 对每道题逐一使用 `school-lab-md-expander`，生成 `实验过程及内容` 的扩写 Markdown。
4. 使用 `school-lab-data-analysis` 根据结果图、表格和指标生成 `数据处理分析` Markdown。
5. 使用 `school-lab-method-conclusion` 生成 `方法、步骤` 和 `实验结论` Markdown。
6. 最后使用 `school-lab-docx-report` 将这些 Markdown 片段转换并填入 Word 模板。

DOCX 写入阶段不再负责临时扩写内容，只负责版式转换、公式渲染、代码/图/表插入和视觉 QA。

## Markdown 迁入不得缩减

已经准备好的 Markdown 是内容来源，不是给 DOCX 阶段“概括”的参考材料。写入 Word 时必须遵守：

1. 不得把 `expanded/`、`analysis/`、`summary/` 中的正文改写成更短摘要。
2. 不得因为版面拥挤、表格单元格较窄或页数变多而删除段落、合并小节、删掉公式、删掉图表或删掉结果解释。
3. 如果内容较长，应通过分页、续表、调整图片尺寸、表格列宽和段落样式解决，不能牺牲内容完整性。
4. 迁入后要用源 Markdown 的小节标题、题号、图表引用和段落数量做对照检查；发现少内容必须重新迁入。
5. 如果必须移动章节边界，例如把扩写稿中的结果材料移到 `数据处理分析`，移动后的内容必须完整保留，不能借移动之名删除。

## 四个主要模块

### 方法、步骤

写成实验设计概要。每道题只写做法，不展开长篇原理。

推荐结构：

```text
一、概念题
1. 对仿射变换、透视变换、插值和 Hough 变换等理论问题进行公式分析。
2. 对不同方法的性质和适用场景进行比较。

二、编程题
1. 根据题目参数建立坐标模型并绘制目标。
2. 对输入图像进行预处理、特征提取、检测和可视化。
3. 保存结果图并分析检测效果。
```

### 实验过程及内容

这是主体。应详细写：

- 题目要求。
- 涉及知识点。
- 原理推导。
- 公式分析。
- 算法步骤。
- 代码设计。
- 代码文本。

概念题不放代码。编程题要放关键代码或完整代码，代码不能截图。

执行要求：

1. 先读取原始 Markdown 初稿。
2. 调用/使用 `school-lab-md-expander` 生成扩写版 Markdown。
3. 将扩写版 Markdown 作为插入 Word 的主要内容来源。
4. DOCX 写入代码只负责转换和排版，不负责把内容压缩成短摘要。
5. 如果 Word 中插入的内容明显少于扩写 Markdown，需要重新插入，不能交付。

### 数据处理分析

这是结果与讨论部分。应包括：

- 结果文件路径。
- 实验结果图片。
- 对应图注。
- 必要的数据表格。
- 程序输出的关键数值。
- 对结果正确性、误差、参数影响的分析。

图像、表格和分析应一一对应。不要只堆图片。

每道题必须尽量保留模板中的结果相关点：`结果文件`、`实验结果展示`、`结果数据表`、`结果分析`、`误差来源与改进`。其中 `结果分析` 是强制重点，只要该题有真实结果证据，就不能少于两到三段实质分析。第一段说明图表或数值展示了什么以及是否满足题目要求；第二段结合算法、参数、阈值、模型或指标解释为什么得到该结果；第三段讨论误差、局限、边界情况和改进方向。若误差分析单独成节，第三段可以与之呼应，但不能把结果分析压缩成一句话。

### 实验结论 / 实验总结

必须使用第一人称完成式。

推荐句式：

```text
通过本次实验，我完成了...
我掌握了...
我实现了...
我对比分析了...
我发现...
```

避免：

```text
你完成了...
本实验让你...
可以看出你...
```

## 格式细则

### 新增正文

- 字体：宋体
- 字号：五号
- 语气：正式、第一人称或客观描述

### 代码

- 代码必须作为可复制的 Word 原生文本插入，不能截图。
- 代码块使用两列表格：左列为行号栏，右列为代码文本。
- 行号栏从实际代码文本自动计算，默认从 1 开始；如果是源文件片段且知道起始行，则从真实起始行开始。
- 行号栏使用 Consolas 8-9pt、右对齐、浅灰文字和浅灰底色；代码栏使用 Consolas 8.5-9pt。
- 代码栏必须保留缩进、空格和空行；tab 统一转换为 4 个空格。
- 按代码语言进行语法高亮，优先使用 Pygments 或等价 lexer。Python/OpenCV/NumPy 代码至少区分关键字、字符串、注释、数字、函数名和普通文本。
- 不要把整个代码块做成单色普通段落。缺少高亮或缺少行号栏都视为代码排版未完成。
- 避免一行过长导致溢出；长行可在代码栏内自然换行，但不能因为视觉换行而新增行号。
- 详细实现规则见 `references/code-blocks.md`。

### 图与图注

- 图片放入数据处理分析或需要说明的实验结果位置。
- 图片宽度以不超出版心为准。
- 图片尺寸采用自适应策略：先读取原图自然尺寸和页面/表格单元格可用宽度，再按内容选择合适宽度。不得把所有图片都强行拉到最大版心宽度。
- 小图不放大到模糊；普通结果图通常控制在正文宽度的 50%-85%；确实需要看细节的综合图才接近版心宽度。
- 插图必须锁定纵横比，不能横向或纵向拉伸变形。
- 图注使用宋体、六号、加粗、居中，不能继承 Calibri、等线或左对齐。
- 图注编号可用：

```text
图 1 xxx
图 2 xxx
```

### 表格

- 使用三线表。
- 表格整体居中。这里的“居中”指整个表格对象在页面正文宽度或所在表格单元格可用宽度内水平居中，不是只把表格内部文字居中。
- 生成 Word 时必须设置表格对象级别的居中属性，例如 python-docx 的 `table.alignment = WD_TABLE_ALIGNMENT.CENTER`，或在 OOXML 的 `<w:tblPr>` 中写入 `<w:jc w:val="center"/>`。
- 单元格段落的 `CENTER` 只能控制单元格文字位置，不能替代表格对象居中；如果只设置单元格文字居中但表格仍贴左边，视为排版失败。
- 表格宽度按内容自适应。短表格不要铺满整行；宽表格才使用接近版心的宽度，并通过列宽、自动换行和字号控制避免挤压。
- 表格不能因为默认 `100%` 宽度显得松散，也不能超过单元格/页面边界。
- 表头加粗。
- 表格文字通常使用宋体五号或按模板局部风格。
- 不要使用全网格线，除非参考模板本身使用。

### 公式

- 公式必须在 Word 中可视化显示。
- 区分 Word 的行内公式和独立显示公式：句中变量和短公式必须作为行内 OMML 留在同一段落中，只有独立公式块才单独居中成段。
- 带上下标或希腊字母的短变量也要当公式处理，例如 `G_x`、`G_y`、`R_{ci}`、`\mu_{R_i}`、`x_i`、`Q_{11}`、`H^{-1}`。如果它们以普通文字出现并触发 Word 拼写波浪线，说明公式渲染失败。
- 不要在最终 DOCX 中留下无法渲染的原始 LaTeX。
- 公式前后应有解释文字。
- 变量必须说明含义和单位。
- 优先使用 Word 原生 OMML 公式结构，即 `m:oMath` 或 `m:oMathPara`。
- 可使用 MathML 经 Microsoft Office 的 `MML2OMML.XSL` 转为 OMML，再插入 DOCX。
- 如果无法生成 OMML，才允许使用高清公式图片作为 fallback，并必须在渲染后检查清晰度。
- 交付前应解压 DOCX 或读取 XML 检查是否存在 `m:oMath`，避免公式仍是普通文本。

## 交给老师的文件整理

最终交给老师的材料应当是一个干净的提交文件夹，而不是完整工作目录。默认结构为：

```text
output/<实验名>_提交材料/
├── <实验名>_实验报告.docx
├── result/
└── code/
```

整理规则：

1. 只放最终报告、`result/` 和 `code/`。除非作业明确要求，不放 `expanded/`、`analysis/`、`summary/`、渲染检查图片、临时 PDF、缓存文件或中间脚本输出。
2. `result/` 使用单数命名，存放报告中引用的最终结果图、最终表格和必要指标文件。不要把所有调试过程图、旧版本结果或 LibreOffice/渲染 QA 图片一股脑放进去。
3. `code/` 存放复现实验结果所需源码、Notebook、辅助模块、配置和必要的小输入样例。不要放虚拟环境、`__pycache__`、`.ipynb_checkpoints`、生成结果、隐藏工具缓存或大型无关数据。
4. 如果工作阶段使用 `results/` 作为原始输出目录，最终提交阶段要筛选并复制到 `result/`，不要把整个原始输出目录原样提交。
5. 交付前列出提交文件夹树，确认没有无关文件，报告中引用的结果文件能在 `result/` 中找到。

## QA 检查清单

交付前检查：

- 封面未被改动。
- 教师批阅、成绩、签名、备注、注释区域未被改动。
- 模板标题未被替换。
- 模板/题目原有图片、绘图对象、公式对象和文本框数量没有减少，特别是题干中的配图没有丢失。
- 新增正文为宋体五号。
- 代码为带左侧行号栏的语法高亮代码表格，Consolas 8.5-9pt，缩进和空行保留。
- 图注为宋体六号加粗居中。
- 表格为整体居中的三线表；渲染图中表格左右留白应基本均衡，不能贴左或只让单元格文字居中。
- `数据处理分析` 中每道题的 `结果文件`、`实验结果展示`、`结果数据表`、`结果分析` 未被 DOCX 写入阶段删减；有真实结果证据时，每题 `结果分析` 至少两到三段。
- 将最终 DOCX 与 `analysis/*.md` 对照，确认图片、表格、结果路径、指标和分析段落没有被摘要化或遗漏。
- 公式可视化正常。
- 图片按自然尺寸自适应，不变形、不越界、不过度铺满。
- 代码不被裁剪，行号连续正确，语法高亮清晰可见。
- 表格按内容自适应，不破线、不挤压、不过度铺满。
- 检查 DOCX 结构时，普通报告表格应在 `w:tblPr` 中具备 `w:jc w:val="center"` 或等效居中属性；视觉检查时，表格整体应在页面/单元格内居中。
- 每页渲染后无重叠、无乱码、无缺字、无异常空白。

## Lab1 样式迁入锁定规则

当用户提供 `Lab1.docx` 或其他已经满意的 Word 报告作为参考时，最终报告的同名区域必须以该文件为版式基准。执行 `实验过程及内容` 迁入前，先解析参考文件中该区域所在的表格单元格、段落、运行和公式结构，并记录以下信息：

1. 区域位置：内容是否在表格单元格、文本框或普通正文中。
2. 段落样式：段前段后、行距、缩进、对齐方式、标题加粗方式。
3. 运行样式：中文字体、英文字体、字号、加粗、代码字体。
4. 公式样式：行内公式是否嵌入同一段落，独立公式是否单独成段并居中。
5. 编号样式：`一、`、`1.`、`(1)`、`1)`、`a.` 的实际显示方式。

写入目标 DOCX 时不要使用通用 Markdown 样式替代参考样式。若目标文件和参考文件结构一致，优先在同一类表格单元格中追加内容，并复制参考区域的段落格式。若必须清空区域重写，重写后的视觉结果仍必须与参考区域一致。

`Lab1.docx` 的典型特征是：主体报告区域在表格单元格内，`实验过程及内容` 与 `数据处理分析` 是不同单元格/段落区域；过程部分有大量原生 OMML 公式，最终 XML 中不应残留 `\frac`、`\sqrt`、`$$` 等原始公式源码。

## 过程区与结果区的强制分离

`实验过程及内容` 只迁入实验设计和实现过程，不迁入实验结果展示。迁入前必须对扩写 Markdown 做一次分区过滤。

保留在 `实验过程及内容` 的内容：

- 题目要求。
- 涉及知识点。
- 算法原理、公式推导、变量说明。
- 公式密集算法或模型结构的定义/假设、中间推导、最终公式、结合题目的例子，以及公式与代码实现的对应关系。
- 算法流程。
- 代码设计、关键代码或完整代码。
- 与代码实现直接相关的参数说明。

移出或禁止迁入 `实验过程及内容` 的内容：

- 标题含有 `实验结果`、`结果展示`、`结果分析`、`数据处理分析`、`实验结果分析`、`输出结果`、`结果文件`、`运行结果` 的小节。
- 结果图片、对比图、误差图、掩膜图、输出截图。
- CSV 指标表、运行日志摘要、精度表、分割结果统计表。
- 图注、表注以及针对实际结果好坏的分析文字。

这些内容应交给 `school-lab-data-analysis` 生成 `数据处理分析`，并在该部分插入图片、三线表和结果解释。过程区最多保留一句客观衔接，例如“实验输出结果在数据处理分析部分给出并讨论”，但不能重复展示结果。注意：从过程区移出结果材料不等于删减结果材料，移出的结果文件、图表、指标和分析文字必须完整进入 `数据处理分析`。

## 公式写入检查

最终 DOCX 中所有公式都必须是可视化公式。这里的“公式”包括独立公式、句中公式、以及带上下标的单个变量。

1. 独立公式：由 `$$...$$` 或单独公式块生成，插入为 OMML，并按参考模板居中。
2. 行内公式：由 `$...$`、`\(...\)` 或自然语言中需要数学排版的符号生成，插入在同一段落内，不能另起一行破坏句子。
3. 带上下标变量：如 `x_i`、`Q_{11}`、`H^{-1}`、`p_k`、`\mu_1`，在数学上下文中也按行内公式处理。
4. 例外：代码块、文件名、路径、函数名、变量名说明中的程序标识符不强制转换。

禁止把 LaTeX 简化成普通字符串再塞进 `m:oMath`。例如把 `\frac{a}{b}` 改成 `(a)/(b)` 后写入 `<m:t>` 不是合格公式。应使用 MathML 到 OMML 的结构转换，或者手写结构化 MathML/OMML 模板。

交付前必须检查：

- `word/document.xml` 中存在预期数量的 `m:oMath` 或 `m:oMathPara`。
- 正文区域没有残留 `$$`、`\(`、`\)`、`\frac`、`\sqrt`、`\sum`、`_{`、`^{` 等原始公式标记。
- 渲染页面中分式、根号、上下标、矩阵、求和号等显示为真实排版结构。

## 题目锚点保留与过程区结构

`实验过程及内容` 中模板或原报告已经存在的题目必须完整保留，包括题号、题干、标点和题目顺序。禁止为了重新排版而删除、改写、合并、缩短或重新编号原题。正确做法是把每个原题段落作为锚点，在该题目下面追加扩写内容。
题干中的图片、绘图对象、公式对象和文本框同样属于题目锚点的一部分。例如编程题 2.5 如果原模板带有题目图片，迁入扩写内容时必须保留该图片与题干的相邻关系，不能只保留文字题干。使用 `python-docx` 时尤其要避免给已有段落或单元格整体赋值，因为这会删除图片所在的 `w:drawing` 运行。

概念题规则：

- 保留 `1.1`、`1.2` 等原题段落。
- 在题目下面直接回答。
- 不添加 `题目分析`、`实验原理`、`实验设计`、`核心代码`、`代码说明`、`本题小结` 等小标题。
- 不为了形式统一而把概念题拆成多级模块。
- 可以使用普通段落和公式完成详细解释。

编程题或实验实现题规则：

- 保留 `2.1`、`2.2`、`3.3` 等原题段落。
- 在每个题目下面依次追加以下加粗小标题，不给这些小标题额外编号：
  - `题目分析`
  - `实验原理`
  - `实验设计`
  - `核心代码`
  - `代码说明`

- 不使用旧结构标题 `题目要求`、`涉及知识点`、`算法流程`、`代码设计与关键代码`、`实验材料与运行方式`、`本题结果和过程解释`、`本题小结` 作为最终 Word 过程区标题。

迁入 DOCX 时，若当前过程区已经有题目，应在这些题目段落后插入内容，不应清空整个单元格后重建题目列表。只有在模板题目缺失或用户明确要求重建时，才允许重新生成题目段落。
